# Lock section blocks, let Claude edit content

The best 10-year standard for BlueWorx client pages is **the normal WordPress block editor, used only as a locked box of our own section blocks**. Each section holds just its words, images, list items and an on/off switch. Our code draws the design every time the page loads, so the design can't drift from Figma. Clients and Claude can change the content and nothing else. This is the approach WSO already uses, and Brodfest already plans to move to it. It needs three things added: proper locks, a safe "edit this section" tool for Claude, and all colours and fonts taken from the theme. The owner asked: "If clients can only edit content, why do we need a visual editor at all?" The honest answer is that we don't need it as a design tool. We keep it because it is the cheapest container WordPress offers for structured content, and the rest of WordPress already understands it. Revisions, drafts, preview, SEO plugins, translation plugins, site search and the coming core AI tools all read page content stored this way. Every alternative means rebuilding those ourselves, and ClubHouse shows what that costs. Separate field forms (ACF, Meta Box or our own editor) come a reasonable second. A Claude-only setup with no editor, and Elementor or hard-coded PHP, should not be used for new work. Nothing here was tested on a live site. This is desk research plus a review of our own repos on 18 November 2026.

## Why keep an editor clients barely touch: it's free plumbing, not a design tool

The owner's challenge is fair. If design is locked and Claude makes most edits, a drag-and-drop canvas adds nothing to the design. But the editor does four jobs that have nothing to do with design, and each one would cost money to replace.

First, **it is where the rest of WordPress looks**. SEO plugins analyse the main page content by default. Content kept in separate fields needs bridge plugins, and even then Yoast's internal-link count and WordPress's own site search ignore it ([WordPress.org: ACF Content Analysis for Yoast](https://wordpress.org/plugins/acf-content-analysis-for-yoast-seo/); [Trac #43867](https://core.trac.wordpress.org/ticket/43867)). Translation plugins carry block content along with the post, while field content needs a translation setting for every field ([WPML: sites built with ACF](https://wpml.org/documentation/related-projects/translate-sites-built-with-acf/)). Content kept as files in git is invisible to all of these unless it is copied back into WordPress. WordPress-side tooling for that is one beta plugin ([PushPull readme](https://cdn.jsdelivr.net/wp/pushpull/tags/0.0.8/README.md)).

Second, **revisions, drafts and preview come free and keep improving**. WordPress 7.0 (May 2026) added side-by-side visual comparison of revisions ([WordPress 7.0 Field Guide](https://make.wordpress.org/core/2026/05/14/wordpress-7-0-field-guide/)). Field content only gets revisions if each field is switched on for them, a feature that has existed since 2023 ([Make Core: meta revisions in 6.4](https://make.wordpress.org/core/2023/10/24/framework-for-storing-revisions-of-post-meta-in-6-4/)). Even then, ACF preview in the block editor has a long record of showing old values ([ACF support](https://support.advancedcustomfields.com/?p=163777)).

Third, **clients still need a way in when Claude isn't available**, and a way to see what they are approving. Every platform running AI editing at scale keeps a human editor alongside the agent and saves agent work as drafts by default. That includes WordPress.com, which since March 2026 asks the user to confirm each write and logs it ([TechCrunch](https://www.techcrunch.com/2026/03/20/wordpress-com-now-lets-ai-agents-write-and-publish-posts-and-more/)). It also includes WordPress VIP, which keeps live-site writes off until an admin turns them on and offers a kill switch ([WordPress VIP Secure MCP](https://wpvip.com/capabilities/ecosystem/secure-mcp/)). No agency was found that removed the human editor from client sites. BlueWorx would be first, with no evidence that clients cope with chat-only editing.

Fourth, and this settles the argument, **our section blocks already are structured fields**. A server-rendered section stores only a name plus a tidy list of values. That is the same shape as a field form, and Claude can edit it reliably because there is no page HTML to keep in step ([Block Editor Handbook: static vs dynamic rendering](https://developer.wordpress.org/block-editor/getting-started/fundamentals/static-dynamic-rendering/)). Since WordPress 7.0, a simple block can be declared in PHP alone, and WordPress builds its edit form automatically ([Make Core: PHP-only block registration](https://make.wordpress.org/core/2026/03/03/php-only-block-registration/)). So the choice is not "visual editor versus structured content". Option A is structured content with a free form and a free preview attached. ClubHouse shows the cost of building that container ourselves. A new page there needs code in five places. Default wording lives in code, so Claude reads something different from what visitors see. The content isn't reachable through the API. And an earlier home-grown builder was withdrawn.

## How the four approaches score over ten years

Scores run from 1 (poor) to 5 (strong), judged against our requirements, not general popularity. A is locked server-rendered section blocks. B is fields plus PHP templates (our own field editor, ACF/SCF or Meta Box). C is no visual editor, with structured content edited only by Claude. C1 keeps it as data inside WordPress with a minimal form. C2 keeps it as files in git. D1 is Elementor and D2 is hard-coded PHP.

| Criterion | A Locked blocks | B Fields + templates | C1 Claude-only, in WordPress | C2 Content as git files | D1 Elementor | D2 Hard-coded PHP |
|---|---|---|---|---|---|---|
| Claude/MCP editing | 4 | 4 if built right (ClubHouse: 2) | 5 | 4 | 2 | 1 |
| Matches Figma exactly | 5 | 5 | 5 | 5 | 2 | 5 |
| Client editing, safely | 4 | 3 | 1–2 | 1 | 2 | 1 |
| Easy new pages | 5 | 3 | 4 | 3 | 3 | 2 |
| Longevity, low lock-in | 5 | 3 | 3 | 2 | 1 | 4 |
| Revisions, drafts, preview | 5 | 3 | 2 | 3 | 3 | 1 |
| Translation | 4 | 4 | 2 | 1 | 3 | 1 |
| SEO tooling | 4 | 2 | 2 | 1 | 3 | 3 |
| Design tokens kept in theme | 5 | 5 | 5 | 5 | 2 | 5 |
| Cost to build and run | 4 | 2 | 2 | 1 | 3 | 3 |
| **Total (of 50)** | **45** | **34** | **31–32** | **26** | **24** | **26** |

**A wins on longevity because WordPress itself carries the maintenance.** Server-rendered blocks never show "this block contains unexpected content" errors. A fix to a section's design reaches every page at once ([Block Editor Handbook](https://developer.wordpress.org/block-editor/getting-started/fundamentals/static-dynamic-rendering/)). The way blocks are stored hasn't changed since 2018, and no roadmap proposes changing it. Real-time co-editing was pulled from 7.0 and is deliberately left off 7.2 ([Make Core: Roadmap to 7.2](https://make.wordpress.org/core/2026/09/18/roadmap-to-7-2/)). Every established WordPress agency with a public view builds marketing pages from custom blocks with locked-down theme settings, not from fields or page builders. That includes Human Made, WebDevStudios, 10up and WordPress VIP. WebDevStudios openly aims to move clients "away from legacy page builders and custom fields" ([WebDevStudios, Nov 2025](https://webdevstudios.com/2025/11/25/a-developers-guide-the-future-of-the-wordpress-gutenberg-block-editor/)). A's real long-term cost is the small editing screen inside each block, which breaks when WordPress upgrades its interface code. A move to React 19 was shipped and then reverted in June 2026 because plugins crashed ([Make Core: React 19 punted](https://make.wordpress.org/core/2026/07/24/react-19-punted-beyond-wordpress-7-1-experiment-in-gutenberg/)). Blocks built the standard way are on the supported path, and blocks declared in PHP alone avoid the problem entirely.

**B is a sound idea weakened by who owns the tools.** The data itself (WordPress's own custom fields) is safe for decades. The trouble is the editing layer. ACF and its WordPress.org fork, Secure Custom Fields, can't run side by side, and the court case behind the split doesn't reach a jury until **19 October 2027** ([webhosting.today, Sep 2026](https://webhosting.today/2026/09/29/automattic-is-not-an-owner-of-the-wordpress-marks-it-asserted-in-court-a-judge-rules/)). Our own field editor avoids that, but we would carry the form screens, preview, SEO bridging and translation settings ourselves for ten years. Every new page would also need work in several places, as ClubHouse shows today.

**C is the tidiest on paper and the most expensive in practice.** Core WordPress offers read-only AI content tools in 7.2 (8 December 2026). Write tools are only a proposal for 7.3, marked "needs decision" with no milestone ([mcp-adapter issue #452](https://github.com/WordPress/mcp-adapter/issues/452)). The official connector that links Claude to WordPress is still pre-1.0 and changed its API in ways that broke existing code in October 2026 ([WordPress/mcp-adapter releases](https://github.com/WordPress/mcp-adapter/releases)). So we must build our own Claude editing tools under every option. C then also needs us to build the client fallback, the preview, the approval step, SEO and translation. Git-based content tools are mature, but they are built for non-WordPress sites. They bring merge conflicts and slow previews that non-technical clients struggle with ([Layer3 Labs, Sep 2026](https://www.layer3labs.io/guides/git-based-cms)). With files in git, every typo fix would also become a deployment.

**D is legacy only.** Elementor's share of WordPress builder sites fell from about **56% to 43%** in a year ([Web Almanac 2025](https://almanac.httparchive.org/en/2025/cms)). Its pages carry two to three times as much page structure as native blocks, by Elementor's own count ([Elementor blog](https://elementor.com/blog/elementor-vs-g/)). Its AI editing works only on the new V4 layouts, and our legacy sites are V3 ([Elementor Help Center, Sep 2026](https://elementor.com/help/how-to-build-and-edit-your-site-using-elementor-mcp/)). Its content breaks if the plugin is switched off ([NexterWP](https://nexterwp.com/blog/elementor-to-gutenberg/)). Hard-coded PHP, as on Brodfest today, matches Figma perfectly but makes every word change a developer job, and Claude can't reach it at all.

## Locking is the weak spot: WordPress's guardrails are soft by default

A's main risk is that **WordPress's locks are built to be stepped around**. By default, anyone who can edit a page can unlock its blocks ([Gutenberg docs: block locking](https://github.com/WordPress/gutenberg/blob/trunk/docs/how-to-guides/curating-the-editor-experience/block-locking.md)). WordPress 7.0 made "content only" editing the default for page patterns, but users can still click "Edit pattern" or "Modify" to get full control ([Make Core: Pattern Editing in 7.0](https://make.wordpress.org/core/2026/03/15/pattern-editing-in-wordpress-7-0/)). WordPress VIP ships a separate governance plugin because the default locks are opt-out ([WordPress VIP: Block governance](https://wpvip.com/blog/block-governance/)). So a real lock needs several layers. Clients can't unlock blocks. The page accepts only our sections, in a fixed order. The raw code view is switched off for client accounts. And the theme switches off every colour, font and spacing control, which is how VIP locks a design system ([WordPress VIP, theme.json](https://develop2.wpvip.com/blog/using-a-design-system-with-the-wordpress-block-editor-pt-1-theme-json/)). The research could not confirm whether the "Modify" escape can be removed for client roles in 7.1. Testing that on WSO is the first job.

Two of our requirements fit core features poorly, and we should handle them inside our own blocks. **Repeating items** (cards, FAQs, team members) can be added and removed under "content only" mode, but only recently. That path still had bugs fixed in April 2026 ([Gutenberg PR #77119](https://github.com/WordPress/gutenberg/pull/77119)). Keeping each section's list inside the section, with its own add/remove/reorder controls, avoids that. **Show/hide** exists in core ([Make Core: Block Visibility in 7.0](https://make.wordpress.org/core/2026/03/15/block-visibility-in-wordpress-7-0/)), but a simple on/off setting on each optional section is easier for Claude to read and impossible to misuse. WordPress's "synced pattern" feature, where one master layout feeds many pages, can't yet handle lists or optional sections, so it isn't needed ([Make Core: Pattern Overrides in 7.0](https://make.wordpress.org/core/2026/03/16/pattern-overrides-in-wp-7-0-support-for-custom-blocks/)).

Claude editing needs one guard of its own. WordPress has no official way to edit a single block. Most connectors swap the whole page as one lump of text, which is how agent edits break block pages ([GravityKit: Block MCP](https://www.gravitykit.com/introducing-block-mcp/)). Our tool should change one named section's values, check them against that section's allowed fields, and save a draft. Because the tool accepts content only and no layout or style fields, even a wrong or manipulated instruction can't break the design. That matters, because instructions hidden inside content an AI reads are the main AI security threat of 2026 ([Toloka](https://toloka.ai/blog/ai-agent-security-guardrails/)).

## What the standard means in practice

For each client site from now on, pages are built only from BlueWorx section blocks. Each block stores content and nothing else, and our code draws it. Blog posts stay in the normal editor, untouched. Clients get in-place text and image editing, list editing inside sections, and on/off switches. They can't add, move or delete sections, pick colours or fonts, or open the code view. New pages start from whole-page layouts with WSO's "Create a page from this layout" button. A genuinely new kind of page means designing new sections, which is developer work by intent. Claude edits through our own tool, one section at a time. Changes are saved as drafts by default, and every write is logged against the person who asked for it, because WordPress's own change log only records the account Claude used. We pin the version of WordPress's AI connector and test it before each upgrade, given its record of breaking changes. Every block reads colours, fonts, sizes and spacing from the theme's published tokens. An automatic style check rejects raw colour values, using the same kind of rule Mozilla and Shopify use ([npm: stylelint-declaration-strict-value](https://npmjs.com/package/stylelint-declaration-strict-value); [Polaris stylelint rules](https://polaris.shopify.com/tools/stylelint-polaris/rules)).

For the existing sites, WSO needs locking and needs its own token file swapped for the theme's. Brodfest should go ahead with its plan for locked blocks with pixel-identical pages. ClubHouse should stop growing the in-house field editor and move to section blocks when it is next rebuilt. Until then, two fixes stop Claude reading content that differs from what visitors see: store the default wording, and expose the content to the API. Elementor sites stay as they are, with no new Elementor builds. AI conversion has moved simple sites in a day, though Pro widgets and exact visuals still needed hand work ([dev.to post-mortem](https://dev.to/rentierdigital/how-to-remove-elementor-from-wordpress-convert-114-pages-to-gutenberg-in-one-day-3iah)).

Three points are unverified and need a test on WSO before the standard is written down. First, whether client roles can be fully locked out of the "Modify" escape in 7.1. Second, whether Yoast and Rank Math score the text inside server-rendered sections, since those plugins analyse saved page content and our text sits inside the block's settings. Third, whether WPML picks up each section's text without extra setup. Search engines see the finished page either way, so the second point affects the editing-screen SEO score only, not rankings.

## Conclusion

The question has quietly changed. The useful divide is no longer "visual editor or forms". It is "content stored where WordPress understands it" versus "content stored somewhere we must support alone". Core WordPress is heading in the same direction from both sides: locked "content only" blocks look more and more like fields, and its AI tools assume content lives in normal page content. Locked section blocks put BlueWorx where the platform is going, so each WordPress release does some of our maintenance for us rather than adding to it. That's what a ten-year standard needs. The editor's visual side is a free bonus, not the reason to choose it.

Some changes would reopen the decision. If client locks can't be made watertight in testing, B's form-only editing becomes the safer client experience, though at a higher build cost. If clients truly never edit and SEO or translation plugins don't matter on a site, C1 (structured content in WordPress, Claude-only, with a minimal form) becomes competitive. If WordPress ships block-aware write tools in 7.3 or later, A gets cheaper still. Only a move away from WordPress hosting per client would make content-as-files worth considering.
